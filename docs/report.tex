\begin{abstract}
We containerised the digital infrastructure of a company with Docker: a shared stack
(web front, certificates, shared disk), a reviews application with its database, cache,
mail relay and backups, a monitoring platform, and the Moodle learning management system.
The same project runs in two environments: a local one on a single machine
(\texttt{compose.yml}) and a production one on a Docker Swarm of seven nodes
(\texttt{production.yml}), in which every user-facing service is replicated, the database
and the cache are clustered and fail over by themselves, and the backups are encrypted and
kept on a node of their own. The images are published in Docker Hub, so deploying only
needs to pull and start them. The report describes the design, the deployment, the
management of data and backups, the monitoring, the test cases and their results.
\end{abstract}

\section{Introduction}

We containerised the infrastructure of Figure~1 of the statement: the shared services
(\emph{basic}), a company application (\emph{app}), an observability platform
(\emph{stats}) and Moodle (\emph{atenea}). As the core application we wrote a review site
in Flask: people leave a comment with a rating from 1 to 5, see the distribution and the
latest reviews, each new comment sends a mail through our SMTP relay and an automatic feeder
collects ratings published in other web pages.

This version goes beyond a single working deployment: every user-facing piece has at least
two replicas on different nodes, the application database and the cache are clustered, the
backups are encrypted and kept on a node of their own, and every service is monitored.
Everything is deployed with one \texttt{docker compose up} (local) or one
\texttt{docker stack deploy} (production), with the images already published in Docker Hub.

The repository contains \texttt{compose.yml} (local), \texttt{production.yml} (swarm), one
folder per image with its Dockerfile and files, \texttt{scripts/} (node labels, publication,
simulated swarm and restore) and this document. The local environment has no TLS and uses
named volumes, but it contains the same clusters (database, cache) as production, so they can
be tested on one machine.

\section{Images and design decisions}

\paragraph{Frontend and cache.} \texttt{nginx:alpine} with the template feature of the
official image (two templates, local and production). Pages of the app are cached for 10~s
in nginx (\texttt{proxy\_cache}, \texttt{proxy\_cache\_lock} and
\texttt{proxy\_cache\_use\_stale}, so users still get an answer while the app is restarting);
static files for one hour. A user that has just posted a review receives the cookie
\texttt{posted} (10~s) which bypasses the cache, so everybody sees their own review at once.
The footer at the bottom left of the page shows \emph{front: <node> / app: <node>}. The name of
the node comes from the swarm template \texttt{\{\{.Node.Hostname\}\}}; the front node is
requested by JavaScript to \texttt{/\_\_node} (not cached) because the HTML itself may be
served from the cache. When the page is refreshed the routing mesh may hand the request to the
other frontend replica and the footer changes.

\paragraph{TLS on 443.} Production serves HTTPS on 443 with a \textbf{self-signed
certificate} on \texttt{localhost}: nginx cannot start without a certificate, so the
entrypoint generates one (key protected with the group passphrase \texttt{groupH},
\texttt{CERT\_PASSWORD}, loaded with \texttt{ssl\_password\_file}) and the browser shows a
warning that has to be accepted. The \svc{letsencrypt} service of the diagram is part of the
stack and has the full logic (\texttt{certbot certonly --webroot}, retries, renewal and
the switch of nginx without a restart), but with a local name it stays idle, because a
certificate authority can only validate a public domain.

\paragraph{Core application.} Python 3.12 slim, non-root, two replicas. The page shows the
average, the distribution of ratings, a paginated list and a form with star rating; the
average is also published as JSON-LD (schema.org), which the feeder reads. The data of each
page is cached in Redis under a key that contains a version number: a new review increments
the version, so stale entries are never read again. If Redis is down the page still works,
because every cache call is inside \texttt{try/except}; if the database is not ready the
answer is a clean 503. \texttt{/healthz} (liveness) and \texttt{/readyz} (database) are used
by the healthchecks and by the probes. Writes go to \texttt{db:5432} (the PostgreSQL leader)
and reads to \texttt{db:5433} (the replicas).

\paragraph{PostgreSQL cluster (Patroni).} Three PostgreSQL 16 nodes (\svc{pg-1},
\svc{pg-2}, \svc{pg-3}) on app1, app2 and stats, each managed by \textbf{Patroni} with a
three-member \textbf{etcd} (\svc{etcd-1..3}, on the same nodes) as consensus store. Patroni
initialises the first node, builds the others as streaming replicas
(\texttt{pg\_basebackup}) and holds the leader key in etcd; if the leader disappears for
\texttt{ttl} = 30~s a replica takes the key and is promoted, and the old leader is
resynchronised with \texttt{pg\_rewind} when it comes back. Three nodes give a majority for
etcd and for the election even if one node is lost, which two nodes could not.
\svc{db} is HAProxy (two replicas): it asks the REST API of Patroni which node is the leader
(\texttt{/primary}) and which are healthy replicas (\texttt{/replica}) and exposes one
stable address, \texttt{db:5432} for the leader and \texttt{db:5433} for the replicas.
Core, Grafana and the backups use only that name, so a failover needs no change anywhere.
Tables and roles are created by the \texttt{post\_bootstrap} script of Patroni on the first
node, not by the application, so several replicas of core starting together cannot collide.
Patroni uses a \emph{fast} checkpoint for the base backup of a new replica, otherwise it
waits for the spread checkpoint (minutes).

\paragraph{Redis cluster.} \svc{redis-1} (master) and \svc{redis-2} (replica) with three
Sentinels (app1, app2, stats; quorum~2). The application asks the Sentinels for the master
(\texttt{redis.sentinel.Sentinel}), so after a failover it finds the new one by itself. The
cache is optional: if Redis disappears the application keeps working, only slower.

\paragraph{Moodle.} \texttt{php:8.3-apache}, release \texttt{4.5.14} \emph{pinned} with its
SHA-256: the file is downloaded with retries, verified and only then extracted, in its own
layer. The entrypoint waits for MariaDB and installs Moodle from the CLI the first time. Only
one container installs: a lock directory in the shared moodledata is the mutex and the
installer touches a heartbeat file every 10~s; if the heartbeat is older than 90~s the
installer died and another container takes the lock (atomic \texttt{mv}), empties the
half-built schema and starts again. The installation is only trusted once the file
\texttt{.installed} exists. Sessions are kept in the database, so any replica serves any
user; \svc{moodle-cron} is the same image running \texttt{cron.php} in a loop.

\paragraph{NFS inside the stack.} A swarm service cannot be \texttt{privileged}, so instead
of the kernel server we use \textbf{NFS-Ganesha} in user space, which only needs two
capabilities (\texttt{DAC\_READ\_SEARCH}, \texttt{SYS\_RESOURCE}, \texttt{cap\_add} of the
stack file) and no kernel module. It runs on the atenea node with a local volume and exports
\texttt{moodledata}, \texttt{letsencrypt} and \texttt{acme} (NFSv4 only, port 2049). The port
is published in \texttt{host} mode on that node only and the other nodes mount it at its
private address (\texttt{NFS\_SERVER}); a task that starts before the server is retried by
swarm.

\paragraph{Backups and observability.} See Sections~\ref{sec:backup} and~\ref{sec:obs}.

\paragraph{Scope of ``production''.} Production means the complete architecture, not
a public service: it runs on our own computer (the seven nodes are simulated with
Docker-in-Docker, Section~\ref{sec:verified}), it is not opened to the Internet and it has no
public domain, so the certificate is self-signed and 443 is served on \texttt{localhost}. A
deployment on a public server with a real domain would only need \texttt{DOMAIN} and
\texttt{LE\_EMAIL}, and certbot would take over; that case is outside this project.

\section{Scalability and high availability}

\subsection{Replicas}

The statement asks every service to be scalable, except cron jobs and DBMS. The stateless
services run with two replicas (one per node) and can be scaled with
\texttt{docker service scale}; Prometheus discovers new replicas with the DNS name
\texttt{tasks.<service>}. The services with one replica are:
\texttt{letsencrypt}, \texttt{backup}, \texttt{moodle-cron} and \texttt{auto} (periodic jobs:
a second copy would only repeat the work), \texttt{moodle-db} (DBMS), \texttt{nfs} (the
shared disk) and \texttt{mailpit} (a development tool). PostgreSQL and Redis are DBMS, and
are clustered instead of scaled (leader and replicas).

\subsection{Failures}

\end{table}

\subsection{Updates}

Updates go one replica at a time (\texttt{stop-first}, \texttt{parallelism: 1}) with
\texttt{failure\_action: rollback}, and are meaningful because the images we build have a
\texttt{HEALTHCHECK}: a new replica must be healthy before the next one is replaced. The
stateless services keep \emph{exactly one replica per node} (\texttt{max\_replicas\_per\_node:
1}), so a node failure never takes both; with that restriction there is no free slot to
start the new replica before stopping the old one, and the other replica serves meanwhile.

\section{Deployment}

We designed two deployment environments: a local environment for development
and testing, and a production environment based on Docker Swarm. Both use the
same images published in \texttt{omarcornejo/lab1grouph} on Docker Hub,
so we can deploy the application without rebuilding the images.
The main differences are how we organize the services, manage storage
and expose the applications to users.

\subsection{Local environment (test)}

For the local environment, we used Docker Compose to run the entire
infrastructure on a single machine. We chose this approach because it
makes it easier to develop and test the different components without
having to manage multiple nodes. Even though everything runs on one
host, we kept the same main services as in production, including the
PostgreSQL and Redis clusters, Moodle and the monitoring platform.

We defined the infrastructure in \texttt{compose.yml}, where we specified
the services, networks and volumes. We used named volumes to keep
persistent data even when containers are stopped or recreated.
For simplicity, we configured the frontend to use HTTP on port~8080,
since we do not need HTTPS certificates for local testing.

Figure~\ref{fig:deploy-local} shows the local deployment. All 29
containers are running, and those with configured healthchecks
report a healthy status. We also confirmed that the reviews application
is accessible through \texttt{http://app.localhost:8080}.

\subsection{Production environment (simulated Swarm)}

For production, we decided to use Docker Swarm to distribute the
infrastructure across seven nodes. Three of them act as managers,
while the other four are workers. Since we did not have seven
physical machines available, we used Docker-in-Docker to simulate
the nodes on a single computer. This allowed us to work with a
distributed architecture without needing additional hardware.

We defined the production configuration in \texttt{production.yml}
and deployed it as a Swarm stack. Unlike the local environment,
we used node labels and placement constraints to control where
each service runs. This way, we could separate the frontend,
application, monitoring, storage and backup services across
different nodes.

We also configured multiple replicas for the services that need
high availability, placing them on different nodes whenever
possible. For the databases and cache, we kept the clustering
mechanisms described in the previous sections.

To allow communication between services running on different
nodes, we used Docker overlay networks. We configured two Nginx
frontend replicas to handle incoming requests and forward them
to the corresponding services. We also enabled HTTPS on
port~443. Since we used \texttt{localhost} instead of a public
domain, we used a self-signed certificate.

Figure~\ref{fig:deploy-production} shows the production deployment.
All seven nodes are in \texttt{Ready} and \texttt{Active} states,
and the services have reached their expected replica counts.
We also accessed the reviews application through
\texttt{https://app.localhost}, where the footer shows which

Databases are not on NFS (locking and network cuts risk corruption). The backup service

data shares a node with its backup. Every night (03:30) it creates a folder with
\begin{itemize}
\item \texttt{app.dump.enc}, \texttt{grafana.dump.enc}: \texttt{pg\_dump -Fc} from the
\emph{replicas} (\texttt{db:5433}, no load on the leader; falls back to the leader), as the read-only role
\texttt{backup};
\item \texttt{moodle.sql.gz.enc}: \texttt{mariadb-dump --single-transaction} with a read-only
MariaDB account;
\item \texttt{moodledata.tar.gz.enc}: moodledata without caches and sessions;
\item \texttt{SHA256SUMS}.
\end{itemize}
Every file is encrypted with AES-256-CBC, PBKDF2 (\texttt{openssl enc}) and the passphrase
of a Docker secret. The folder is written as \texttt{.partial} and renamed at the end, so an
interrupted backup is never mistaken for a good one. Folders older than 14 days are removed.

\paragraph{Automatic restore test.} Every Sunday (and on demand with
\texttt{docker exec <backup> /restore-test.sh}) the latest backup is verified: checksums,
decryption, restoration of the application dump into a throw-away PostgreSQL started inside
the container and of the Moodle dump into a throw-away MariaDB, and a count of rows and
tables. The result is published as metrics (\texttt{backup\_restore\_test\_ok}, rows,
tables) that Prometheus scrapes, with alerts if the last backup is older than 25~h or the
test fails. The result is the number of reviews and of Moodle tables recovered.

Restoring: \texttt{scripts/restore.sh <folder> app|grafana|moodle|moodledata}.

\section{Security}

\begin{itemize}
\item Only nginx is exposed; port 80 serves ACME challenges and redirects to HTTPS
(TLS 1.2/1.3, HSTS). Moodle, Grafana and the app are reached only through it.
\item \textbf{Database roles with least privilege}: \texttt{app} owns database
\texttt{app} and \texttt{grafana} owns its own; \texttt{replicator} (created by Patroni) can only replicate;
\texttt{backup} has \texttt{pg\_read\_all\_data}; \texttt{exporter} has \texttt{pg\_monitor};
nobody uses the superuser, and \texttt{CONNECT} is revoked from \texttt{PUBLIC}. MariaDB has
separate read-only \texttt{exporter} and \texttt{backup} accounts.
\item Passwords are Docker secrets mounted in \texttt{/run/secrets}. All overlay networks
are encrypted (IPsec) and each stack is isolated in its own network.
\item The SMTP relay is not published; \texttt{/metrics} is blocked in nginx. The only
other published page is the mail catcher (\texttt{mail.localhost:8080}), plain HTTP and
without login, which is acceptable in the laboratory because it only holds notification mails.
\item Backups are encrypted and verified.
\end{itemize}

\section{Results}

\subsection{Local environment}

The whole stack starts with two commands (\texttt{docker compose pull} and
\texttt{docker compose up -d}) and in less than a minute the 29 containers are healthy
(Moodle needs about three minutes the first time, because it installs itself). The
application works end to end: a review is stored in PostgreSQL, appears at once on the page,
generates a mail that can be read in Mailpit, and updates the dashboards of Grafana. The
database and the cache survive the loss of their main node: stopping the PostgreSQL leader
makes another node take its place in a few seconds (about 3~s if the container is stopped,
about 28~s if it is killed), and stopping the Redis master promotes its replica; in both
cases the application keeps accepting reviews and no review is lost. The backup is encrypted
and the automatic restore test recovers the reviews and the 494 tables of Moodle.

\subsection{Production environment (\texttt{production.yml})}
\label{sec:verified}

Production is the same stack spread over seven nodes. It runs on our own computer: the nodes
are seven Docker-in-Docker containers (\texttt{scripts/sim-swarm.sh}), three of them swarm
managers. All the services
reach their replicas and each one is on the node that its label asks for. What we obtained:
\begin{itemize}
\item \textbf{Entry:} the three sites answer on 443 through both front nodes (self-signed
certificate) and port 80 redirects; requests are spread over front1/front2 and app1/app2.
\item \textbf{Loss of a whole node (app2):} swarm detects it in 13~s, a database replica is
promoted, the page keeps answering and reviews are accepted again once the election ends;
when the node returns, its database rejoins as a replica without intervention.
\item \textbf{Loss of a front node:} the other front serves all the sites.
\item \textbf{Rolling update:} the frontend was replaced replica by replica while a request
was sent every half second, and none failed.
\item \textbf{Mail, Atenea and Grafana:} the mail of a new review is listed in
\texttt{http://mail.localhost:8080}, a course created in Atenea is stored (log and database)
and both Prometheus replicas see all their targets up.
\item \textbf{Backups:} made from a database replica on the backup node, encrypted, and the
restore test passes (reviews and 494 Moodle tables).
\end{itemize}
\section{Limitations}

\begin{itemize}
\item \textbf{Production is simulated on one computer.} The seven nodes are
Docker-in-Docker containers, so the behaviour with the latency of separate machines is not
measured. It is not opened to the Internet and has no public domain: the certificate is
self-signed (the Let's Encrypt logic is in the stack but stays idle).
\item \textbf{Quorum.} PostgreSQL and etcd need two of their three nodes; if two fail at the
same time, writes stop until one returns. The third PostgreSQL node shares its machine with
the monitoring.
\item \textbf{Single instances.} MariaDB, the NFS server and the mail catcher have one
instance (the statement exempts DBMS); losing the atenea node stops Moodle until it returns.
\item \textbf{Backups} are kept on one disk of one node; there is no off-site copy.
\item \textbf{Security simplifications of the laboratory.} All the secrets are
\texttt{groupH} and are committed; NFS uses \texttt{no\_root\_squash} (limited to private
networks) and its port must be closed in a firewall; the mail catcher has no login.
\end{itemize}

\section{Conclusions}

The goal of the project was to turn the infrastructure of a company into a set of small
services that can be started anywhere with a couple of commands, and to prove that it keeps
working when something breaks. We have a complete system: a reviews application, a learning
platform, monitoring, mail and backups, all packaged as images that anyone can download and
run, on one machine for development or on seven nodes for production.

The part that taught us most was not starting the services but making them survive failures.
In a distributed system the pieces have to find each other, agree on who is in charge and
recover without anybody touching them, and many of the problems we found appeared only when
we switched machines off on purpose. Testing those failures from the beginning, and not at
the end, saved us from believing that something worked just because it had started.

The result is a system where losing a web server, an application server, the cache or the
database leader goes unnoticed by the user, and where the data is protected by encrypted
copies that are checked automatically by restoring them. It is not a public service and it
keeps some simplifications that a real company would not accept, which are listed in the
previous section, but the structure is the same one that would be used with real machines:
the next steps would be to move it to servers with a real domain, to keep a copy of the
backups outside, and to manage the passwords properly.
