\begin{abstract}
We containerised the digital infrastructure of a company with Docker: a shared stack
(web front, certificates, shared disk), a reviews application with its database, cache,
mail relay and backups, a monitoring platform, and the Moodle learning management system.
The same project runs in two environments: a local one on a single machine
(\texttt{compose.yml}) and a production one on a Docker Swarm of seven nodes
(\texttt{production.yml}), in which every user-facing service is replicated, the database
and the cache are clustered and fail over by themselves, and the backups are encrypted and
kept on a node of their own. The images are published in Docker Hub, so deploying only
needs to pull and start them. The report describes the design, the deployment, the
management of data and backups, the monitoring, the test cases and their results.
\end{abstract}

\section{Introduction}

We containerised the infrastructure outlined in the laboratory assignment: the shared services
(\emph{basic}), a company application (\emph{app}), an observability platform
(\emph{stats}), and Moodle (\emph{atenea}). For the core application, we developed a reviews
service in Flask: users can post comments with a 1-to-5 rating, view score distributions and
recent reviews, trigger email notifications through an internal SMTP relay upon each submission,
and ingest external ratings via an automated background feeder.

The implementation is designed for production-grade resilience: every user-facing component
maintains at least two replicas distributed across distinct nodes, the application database
and caching layers are clustered with automatic failover, backups are encrypted and stored on
a dedicated node, and all services export health and telemetry metrics. Deployment is
fully automated, requiring only a single \texttt{docker compose up} for local execution or
\texttt{docker stack deploy} for production Swarm orchestration, using pre-built images published
to Docker Hub.

The repository is organised into \texttt{compose.yml} (local), \texttt{production.yml} (Swarm),
service directories containing their respective \texttt{Dockerfile} definitions and runtime
assets, helper automation in \texttt{scripts/} (node labelling, image publishing, Swarm simulation,
and disaster recovery), and this report. The local environment operates without TLS and uses
named volumes, yet preserves the exact clustering topology present in production to enable verification on a single development machine.

\section{Images and design decisions}

\paragraph{Frontend and caching.} We use \texttt{nginx:alpine} as the single public entrypoint for all services. Nginx terminates TLS, routes subdomains to their internal services, and caches dynamic pages for 10~seconds and static files for one hour. When a user submits a review, a temporary cookie bypasses the cache so their new comment appears immediately. The page footer displays which frontend and application nodes handled the request, demonstrating load distribution across replicas.

\paragraph{TLS and certificates.} Production exposes HTTPS on port 443 using a self-signed certificate generated at container startup, allowing Nginx to boot without external dependencies. The \svc{letsencrypt} service is fully defined in the stack with automated renewal logic, but remains idle when running with local domains (\texttt{localhost}) where public certificate authorities cannot validate ownership.

\paragraph{Core application.} The reviews application is built with Python 3.12 and runs as a non-root user with two replicas. To maintain high performance, page data is cached in Redis with version-based invalidation upon new submissions. The application degrades gracefully: if Redis is unreachable, requests fall back directly to the database; if the database is temporarily recovering, the service returns a clean HTTP 503 instead of crashing. Database operations are decoupled via HAProxy: writes target the leader (port 5432) while reads are distributed across replicas (port 5433).

\paragraph{PostgreSQL cluster (Patroni).} Database high availability is managed by Patroni across three PostgreSQL 16 nodes (\svc{pg-1}, \svc{pg-2}, \svc{pg-3}) distributed over \texttt{app1}, \texttt{app2}, and \texttt{stats}. A three-node etcd cluster provides distributed consensus for leader election and health tracking. If the active leader fails, Patroni automatically promotes a replica within seconds. HAProxy (\svc{db}) sits in front of the cluster, continuously querying Patroni's health API to expose consistent endpoints (\texttt{db:5432} for writes, \texttt{db:5433} for reads) so application services require no configuration changes during a failover.

\paragraph{Redis cache and Sentinel.} Redis caching uses a primary-replica architecture paired with three Redis Sentinels across separate nodes (quorum of 2). The application dynamically discovers the active master through Sentinel, enabling automatic failover if the primary node goes offline.

\paragraph{Moodle LMS.} Moodle 4.5 LTS is deployed using PHP 8.3 Apache with two replicas. On initial launch, an automated script runs the command-line installer, utilizing a filesystem lock in the shared volume to prevent race conditions between containers. User sessions are persisted in MariaDB, allowing any replica to serve incoming requests interchangeably. A dedicated container (\svc{moodle-cron}) runs scheduled tasks in the background.

\paragraph{Shared storage (NFS).} Because Docker Swarm restricts privileged containers on worker nodes, we deploy \textbf{NFS-Ganesha} in user space on the \texttt{atenea} node. It exports shared volumes for Moodle data and certificates using only standard Linux capabilities, enabling seamless multi-node file sharing without requiring kernel-level NFS modules on the host.

\paragraph{Backups and observability.} See Sections~\ref{sec:backup} and~\ref{sec:obs}.

\paragraph{Scope of production.} In the context of this project, ``production'' represents the complete multi-node Swarm architecture running on local Docker-in-Docker nodes. Because it is evaluated locally rather than on a public cloud provider, services use \texttt{localhost} subdomains and self-signed certificates.

\section{Scalability and high availability}

\subsection{Replicas}

The project guidelines require all services to be scalable, excluding periodic jobs and non-distributed DBMS. Stateless components (\svc{frontend}, \svc{core}, \svc{static}, \svc{db}, \svc{smtp}, \svc{grafana}, \svc{moodle}, and \svc{prometheus}) are deployed with two replicas and can be dynamically scaled using \texttt{docker service scale}. Prometheus automatically discovers active replicas via Docker Swarm DNS (\texttt{tasks.<service>}).

Services intentionally kept at a single replica include periodic background jobs (\svc{letsencrypt}, \svc{backup}, \svc{moodle-cron}, and \svc{auto}, where duplicate runs would be redundant), single-host storage (\svc{nfs}), developmental tooling (\svc{mailpit}), and \svc{moodle-db}. The primary stateful layers (PostgreSQL and Redis) are not scaled naively, but are deployed as high-availability clusters with automated leader election and replication.

\subsection{Updates}

Updates are applied one container at a time (\texttt{parallelism: 1}, \texttt{order: stop-first}) with automated rollback upon error (\texttt{failure\_action: rollback}). Each custom image includes a defined \texttt{HEALTHCHECK}, guaranteeing that an updated replica is verified healthy before the deployment progresses to the next node. Furthermore, stateless services enforce \texttt{max\_replicas\_per\_node: 1}, ensuring replicas reside on distinct physical hosts so that a single host failure never compromises service availability.

\section{Deployment}

We designed two deployment environments: a local environment for development
and testing, and a production environment based on Docker Swarm. Both use the
same images published in \texttt{omarcornejo/lab1grouph} on Docker Hub,
so we can deploy the application without rebuilding the images.
The main differences are how we organize the services, manage storage
and expose the applications to users.

\subsection{Local environment (test)}

For the local environment, we used Docker Compose to run the entire
infrastructure on a single machine. We chose this approach because it
makes it easier to develop and test the different components without
having to manage multiple nodes. Even though everything runs on one
host, we kept the same main services as in production, including the
PostgreSQL and Redis clusters, Moodle and the monitoring platform.

We defined the infrastructure in \texttt{compose.yml}, where we specified
the services, networks and volumes. We used named volumes to keep
persistent data even when containers are stopped or recreated.
For simplicity, we configured the frontend to use HTTP on port~8080,
since we do not need HTTPS certificates for local testing.

containers are running, and those with configured healthchecks

\subsection{Production environment (simulated Swarm)}

For production, we decided to use Docker Swarm to distribute the
infrastructure across seven nodes. Three of them act as managers,
while the other four are workers. Since we did not have seven
physical machines available, we used Docker-in-Docker to simulate
the nodes on a single computer. This allowed us to work with a
distributed architecture without needing additional hardware.

We defined the production configuration in \texttt{production.yml}
and deployed it as a Swarm stack. Unlike the local environment,
we used node labels and placement constraints to control where
each service runs. This way, we could separate the frontend,
application, monitoring, storage and backup services across
different nodes.

We also configured multiple replicas for the services that need
high availability, placing them on different nodes whenever
possible. For the databases and cache, we kept the clustering
mechanisms described in the previous sections.

To allow communication between services running on different
nodes, we used Docker overlay networks. We configured two Nginx
frontend replicas to handle incoming requests and forward them
to the corresponding services. We also enabled HTTPS on
port~443. Since we used \texttt{localhost} instead of a public
domain, we used a self-signed certificate.

Figure~\ref{fig:deploy-production} shows the production deployment.
All seven nodes are in \texttt{Ready} and \texttt{Active} states,
and the services have reached their expected replica counts.

Databases are not on NFS (locking and network cuts risk corruption). The backup service
lives on a node that is neither an app node nor the NFS node, with its own disk, so no live
data shares a node with its backup. Every night (03:30) it creates a folder with
\begin{itemize}
\item \texttt{app.dump.enc}, \texttt{grafana.dump.enc}: \texttt{pg\_dump -Fc} from the
\emph{replicas} (\texttt{db:5433}, no load on the leader; falls back to the leader), as the read-only role
\texttt{backup};
\item \texttt{moodle.sql.gz.enc}: \texttt{mariadb-dump --single-transaction} with a read-only
MariaDB account;
\item \texttt{moodledata.tar.gz.enc}: moodledata without caches and sessions;
\item \texttt{SHA256SUMS}.
\end{itemize}
Every file is encrypted with AES-256-CBC, PBKDF2 (\texttt{openssl enc}) and the passphrase
of a Docker secret. The folder is written as \texttt{.partial} and renamed at the end, so an
interrupted backup is never mistaken for a good one. Folders older than 14 days are removed.

\paragraph{Automatic restore test.} Every Sunday (and on demand with
\texttt{docker exec <backup> /restore-test.sh}) the latest backup is verified: checksums,
decryption, restoration of the application dump into a throw-away PostgreSQL started inside
the container and of the Moodle dump into a throw-away MariaDB, and a count of rows and
tables. The result is published as metrics (\texttt{backup\_restore\_test\_ok}, rows,
tables) that Prometheus scrapes, with alerts if the last backup is older than 25~h or the
test fails. The result is the number of reviews and of Moodle tables recovered.

Restoring: \texttt{scripts/restore.sh <folder> app|grafana|moodle|moodledata}.

\section{Security}

\begin{itemize}
\item Only nginx is exposed; port 80 serves ACME challenges and redirects to HTTPS
(TLS 1.2/1.3, HSTS). Moodle, Grafana and the app are reached only through it.
\item \textbf{Database roles with least privilege}: \texttt{app} owns database
\texttt{app} and \texttt{grafana} owns its own; \texttt{replicator} (created by Patroni) can only replicate;
\texttt{backup} has \texttt{pg\_read\_all\_data}; \texttt{exporter} has \texttt{pg\_monitor};
nobody uses the superuser, and \texttt{CONNECT} is revoked from \texttt{PUBLIC}. MariaDB has
separate read-only \texttt{exporter} and \texttt{backup} accounts.
\item Passwords are Docker secrets mounted in \texttt{/run/secrets}. All overlay networks
are encrypted (IPsec) and each stack is isolated in its own network.
\item The SMTP relay is not published; \texttt{/metrics} is blocked in nginx. The only
other published page is the mail catcher (\texttt{mail.localhost:8080}), plain HTTP and
without login, which is acceptable in the laboratory because it only holds notification mails.
\item Backups are encrypted and verified.
\end{itemize}

\section{Results}

\subsection{Local environment}

The stack is started with \texttt{docker compose pull} and \texttt{docker compose up -d},
and the 29 containers become healthy in under a minute (Moodle takes around three minutes
on the first run because of its installation). The application works end to end: a new
review is stored in PostgreSQL, shown on the page, sends a mail visible in Mailpit and
updates the Grafana dashboards. When the PostgreSQL leader is stopped, another node takes
over in about 3~s (about 28~s if the container is killed), and stopping the Redis master
promotes its replica. In both cases reviews are still accepted and none are lost. Backups
are encrypted, and the automatic restore test recovers the reviews and the 494 Moodle tables.

\subsection{Production environment (\texttt{production.yml})}
\label{sec:verified}

Production runs the same stack on seven nodes, simulated on a single computer with
Docker-in-Docker containers (\texttt{scripts/sim-swarm.sh}), three of them acting as swarm
managers. Every service reaches its replica count and is placed on the node given by its
label. The tests gave the following results:
\begin{itemize}
\item The three sites answer on port 443 through both front nodes (self-signed
certificate), port 80 redirects, and traffic is balanced across front1/front2 and app1/app2.
\item When app2 is shut down, swarm detects it in 13~s and a database replica is promoted.
The page stays up and reviews are accepted again after the election. When the node comes
back, its database rejoins as a replica automatically.
\item If one front node fails, the other one serves all the sites.
\item A rolling update of the frontend, with a request every 0.5~s, finished with no
failed requests.
\item Review mails appear in \texttt{http://mail.localhost:8080}, courses created in Atenea
are stored, and both Prometheus replicas see all their targets up.
\item Backups are taken from a database replica on the backup node, encrypted, and pass
the restore test.
\end{itemize}

\section{Limitations}

\begin{itemize}
\item Production is simulated on one machine, so real network latency between nodes was
not measured. It is not exposed to the Internet and has no public domain, so the
certificate is self-signed (the Let's Encrypt configuration is included but unused).
\item PostgreSQL and etcd need two of their three nodes. If two fail together, writes stop
until one recovers. The third PostgreSQL node also hosts the monitoring.
\item MariaDB, the NFS server and the mail catcher run as single instances, so losing the
atenea node stops Moodle until it returns.
\item Backups are stored on a single disk with no off-site copy.
\item For simplicity, all secrets are \texttt{groupH} and are committed to the repository,
NFS uses \texttt{no\_root\_squash} (restricted to private networks, its port should be
firewalled) and the mail catcher has no authentication.
\end{itemize}

\section{Conclusions}

We turned a company infrastructure into a set of containerised services that can be
deployed with a couple of commands, either on one machine for development or on seven
nodes for production. The system includes the reviews application, Moodle, monitoring,
mail and encrypted backups, all published as images.

The hardest part was not getting the services to start but making them tolerate failures:
service discovery, leader election and automatic recovery. Many issues only showed up when
we deliberately stopped nodes, so testing failures early was essential. In the final
system, losing a web server, an application server, the cache or the database leader is
transparent to the user, and backups are verified by automatic restores.

The deployment still has the simplifications listed above, but its architecture would be
the same on real hardware. Future work would be deploying it on real servers with a public
domain, keeping off-site backups and proper secret management.
